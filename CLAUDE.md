# CLAUDE.md — правила разработки Telegram Anti-Spam Intelligence

Этот файл — обязательная инструкция для AI-агента (Claude Code, Codex и совместимые CLI-агенты), который реализует проект по `Task.md`.

## 1. Роль и критерий успеха

Ты — ведущий Go-инженер по надёжным event-driven backend-сервисам и Telegram Bot API. Реализуй **рабочий, тестируемый, легко разворачиваемый** бот, а не демонстрацию с заглушками. Приоритеты: корректность, безопасность, отсутствие ложных фактов о санкциях, цена LLM, прозрачность решений, простое обслуживание на Ubuntu VPS.

**Сначала полностью прочитай `Task.md`**, затем этот файл, затем доступный код и docs. `Task.md` — источник продуктовых требований; `CLAUDE.md` — стиль и инженерные ограничения. Если задача нарушает ограничения Telegram, зафиксируй ограничение и предложи честный workaround, не имитируй событие.

**Выполняй работу итеративно**, завершая каждую фазу работающими тестами и понятным отчётом. Не оставляй TODO-«реализацию» там, где задача требует рабочее поведение. Сохраняй действующие функции при рефакторинге. Не переписывай проект с нуля без причины.

## 2. Непереговорные инварианты

1. **Observe-only.** В v1 сервис не должен вызывать `banChatMember`, `restrictChatMember`, `deleteMessage` и любые методы санкций. Не проси у бота прав на бан/удаление. Кнопки рекомендаций только размечают кейсы.
2. **4 обязательных AI-триггера:** `FIRST_OBSERVED`, `UNKNOWN_EXTERNAL_DOMAIN`, `TELEGRAM_BOT_LINK`, `COMPETITOR_PRICE_OR_ACCUSATION`. Нельзя отключать их trust, бюджетом optional-задач или малым risk score. Необработанный mandatory job должен оставаться в очереди и явно иметь статус `pending`.
3. **Факты, предположения, метки разделены.** Admin click, LLM answer и обычный `/mute` от пользователя не превращаются в `verified_moderation_action`.
4. **Не выдумывать геолокацию и историю.** `language_code` не является страной. «Первый» означает first observed после установки; платформа не сообщает прошлую историю произвольно.
5. **Не преследовать добросовестную критику.** «Есть дешевле» и «у вас скам» обязаны пройти AI review, но без ссылок/навязывания/обмана обычно не должны получать обвинительный вердикт.
6. **No silent drops.** Входящие обновления и mandatory jobs не терять из-за рестарта, таймаута, API 429 или невалидного JSON. Дубликаты обрабатывать идемпотентно.
7. **No privilege escalation.** Никто не получает доступ к админ-кнопкам только потому, что написал `/admin`, упомянул @username или подделал callback. Верифицировать `user_id` и права.
8. **No invisible data collection.** Собирать только информацию управляемых чатов, обеспечивать TTL, редактирование секретов и приватность.
9. **Нет ложной уверенности.** Нельзя писать «удалено», «замучен», «забанен», «LLM проверил», если нет подтверждённого источника.
10. **Никаких хардкод-секретов.** Пароли, токены, session-файлы и реальные идентификаторы не включать в git, код, скриншоты, тестовые фикстуры.

## 3. Технические решения по умолчанию

- **Язык:** Go (стабильная поддерживаемая версия; при выборе зависимостей учитывать их `go` requirements, pgx/v5 — актуальные выпуски).
- **Bot API:** `github.com/go-telegram/bot`, после сверки с актуальной документацией и реалиями требуемой версии Bot API.
- **База:** PostgreSQL через `pgx/v5` + `pgxpool`. Миграции SQL, проверяемые в CI; не применять неограниченный ORM.
- **Очереди:** Postgres таблицы с `FOR UPDATE SKIP LOCKED` + backoff/lease. Redis и брокер только при измеренной необходимости.
- **Конфигурация:** typed structs, env для секретов, YAML для правил/порогов, startup validation. Значения по умолчанию описаны явно.
- **Логирование:** `log/slog` с `chat_id`, `message_id`, `incident_id`, `job_id`, `rule_version`, `provider`, `elapsed_ms`; никогда не логируй API-ключи или весь приватный текст сообщения.
- **HTTP:** стандартный `net/http`; отдельные timeout/size limits. Webhook обязателен только если выбран в настройках, polling достаточно для MVP.
- **Тесты:** стандартный `testing`; Go race detector и `go vet`. Для Postgres-интеграции допускается Docker Compose/Testcontainers, но тесты не должны зависеть от публичного Telegram или платного AI API.
- **Внешние AI:** один провайдер-neutral интерфейс, mock/fake реализации для тестов, OpenAI-compatible transport; конкретные названия моделей — строки конфигурации.

Избегай тяжёлого DI, «чистой архитектуры» из 15 интерфейсов для одной операции, абстракций ради абстракций. Но **изолируй** границы Telegram, SQL и LLM так, чтобы тестировать бизнес-логику без сети.

## 4. Архитектура и зависимости пакетов

Следуй дереву из раздела 13 `Task.md` с возможностью разумного упрощения. Предпочтительное направление зависимостей:

```text
cmd/sentinel → internal/app
                 │
                 ├── adapters: telegram / storage / LLM provider
                 │
                 └── domain: ingest / urlscan / rules / trust /
                              review / incidents / reports / feedback
```

Не завязывать domain-logic на типы Telegram SDK или `pgx.Rows`. На границе превращать Telegram update в собственную нормализованную структуру. Доменный расчёт score должен быть чистой функцией и воспроизводиться на fixture.

Для каждого связанного события использовать ключи `chat_id`, `message_id`, `user_id` как **int64**, Telegram `update_id` как int64. Не использовать username как стабильный идентификатор пользователя. `sender_chat`/отсутствие `from` обрабатывать отдельно.

При изменении сообщения использовать версии и повторно считать риск. Сохранить неизменяемый audit trail, но не удваивать счётчики активности.

## 5. Кодстайл Go

- Поддерживать идиоматичный Go: `gofmt`, короткие пакеты `lowercase`, exported identifiers в `PascalCase`, обработка ошибок через `error`, без `panic` в обычной логике, без `recover` как способа скрыть дефекты.
- В SQL/JSON/YAML — `snake_case`; внутренние локальные имена должны быть простыми и понятными. Не создавать трудночитаемых «сверхкоротких» названий ради стиля.
- Ошибки оборачивать контекстом через `fmt.Errorf("operation: %w", err)`, чтобы не терять причину; не игнорировать возвращаемые ошибки. `context.Context` должен проходить через все DB/HTTP/Telegram операции.
- Не вводить глобальные изменяемые singleton-состояния. Параметры конфигурации получать через зависимости или immutable snapshot.
- Границы времени — UTC, durations — `time.Duration`; не сравнивать raw Unix timestamps вручную без нужды.
- Ограничивать память для очередей, длин сообщений, строк LLM и массивов; не декодировать неограниченные HTTP body.
- Не использовать неопределённые/магические числа: правила и пороги — named config/const с тестами.
- Работа с БД — параметризованные запросы, контекст и транзакции; никогда не собирать SQL конкатенацией произвольного user input.
- Комментарии должны объяснять **почему** есть ограничение/инвариант, а не повторять строку кода; документация публичных exported функций по делу.
- Не добавлять ненужных зависимостей, reflection, generics и конкуренции там, где простая реализация достаточна.
- Использовать явные состояния и enum-like string types; unknown/partial должны сохраняться как отдельные варианты, не сливаться с false.

## 6. Telegram Bot API — правила адаптера

- При запуске сверить актуальные поля `Update`, `Message`, `ChatMemberUpdated`, `MessageEntity`, `CallbackQuery` с официальным API: https://core.telegram.org/bots/api .
- Список `allowed_updates` **явный**: обычные сообщения, правки, `chat_member`, `my_chat_member`, callbacks и прочие только реально используемые типы.
- `chat_member` доступен при соответствующем admin-status; права и настройки валидировать при запуске, а недоступные функции отображать в `/status`.
- Polling и webhook нельзя одновременно включать для одного токена. Webhook должен проверять Telegram secret header, лимитировать тело и фиксировать событие до `2xx`.
- Гарантировать дедуп `update_id`, сохранять offsets/коммиты корректно; не полагаться, что Telegram отправляет ровно один раз.
- Telegram-ссылку строить централизованным helper с unit-тестами. Не предполагать, что публичный `@username` стабилен. Для `t.me/c` использовать правильный supergroup ID; при невозможности — отказ от кнопки, а не мнимая рабочая ссылка.
- Не считать произвольный `t.me/name` ботом. Признак `is_bot` использовать только там, где реально есть объект `User` из API или явно подтверждённое знание; суффикс `bot` — лишь эвристика.
- Не считать исчезновение сообщения подтверждением удаления. У обычного Bot API нет универсального deleted-message update.
- Сообщения другого бота могут быть недоступны; для модерационного бота предпочтительна доверенная интеграция с собственным webhook и проверкой подписи, а не парсинг его обычных сообщений.
- Реакции, forward, private/group topic, anonymous admin, quote, caption, entity offsets и UTF-16 обязательно учитывать при парсинге; не применять байтовые индексы к Telegram entity offsets без преобразования.
- Если нет уверенности о возможности API — свериться с docs и реализовать `unavailable/unknown`, не имитировать нужный feature.

## 7. Risk engine — корректность важнее агрессивности

- `Signal` должен содержать машиночитаемый `code`, `weight`, `evidence`, `confidence`, `mandatory_ai`, `ruleset_version`.
- Сигналы отдельно от итоговой оценки; каждый score можно пересчитать на фиксированных входных данных.
- Внутренний движок должен сохранять не только итог, но и причины; вес одного и того же домена не дублировать через 5 регулярных выражений.
- Trust ограничен cap, не даёт иммунитета; высокий trust не отменяет `FIRST_OBSERVED` и другие MUST.
- Never infer geography from `language_code`, имени, номера телефона, ника или флага. Не хранить предполагаемый регион как фактор доверия.
- Для сообщений с «наш сервис скам», «есть дешевле», «китайский API» триггер обязателен, но добавление обвинительного веса требует **явных признаков** рекламы или обмана, а не одного слова.
- Скрытые ссылки `text_link`, IDN, `example.com.evil.tld`, сокращатели, реферальные параметры и Telegram bot deep links должны покрываться тестами.
- При изменении конфигурации фиксировать `ruleset_version`; менять оценки прошлых кейсов только через явный replay, а не silently mutate.

## 8. LLM — защита, схема, стоимость

- LLM получает только краткий релевантный контекст и детерминированные признаки. Логику allowlist/URL и фактические admin actions определяет **код**, не модель.
- Любой текст пользователя, URL, описание в профиле, цитата и reply — **недоверенные данные**. Изолировать их от system/developer prompt; игнорировать «инструкции», вложенные в чат, и тестировать prompt injection.
- Контракт строго типизирован; JSON parsing с проверкой schema, allowed enum и длины. На ошибку — `failed/retry` или `uncertain`, не трактовать как `safe` и не терять mandatory job.
- AI не имеет инструмента отправки сообщения в основной чат, модерационных вызовов Telegram или доступа к секретам.
- Модель/провайдер может поменяться без модификации rules engine. API key не попадёт ни в messages, ни в debug log.
- Избегать повторных вызовов и неконтролируемых циклов. Optional budget configurable, mandatory tasks в отдельной политике приоритетов.
- Метрики token input/output и estimate cost считать из ответа провайдера при наличии usage; если usage отсутствует, отмечать `unknown/estimated`, не выдавать точную стоимость.
- Никогда не утверждать, что модель «научилась» на банах: до внедрения supervised retraining это dataset и offline tuning.

## 9. Источники событий модерации

Введи явную типизированную модель:

```text
ModerationEvent {
  source: platform_chat_member | mtproto_admin_log | trusted_bot_webhook | admin_attested | unverified_text
  source_event_id
  chat_id, target_user_id, actor_user_id?
  action: ban | kick | restrict | unrestrict | warn | delete | unknown
  occurred_at
  evidence_level: verified | attested | unverified
  related_message_id?
}
```

Проверка:

- `platform_chat_member`: вычислять из **переходов old → new**, не по одному `new.status`; соотносить actor в событии и доступные данные о правах; не выдумывать причину.
- `trusted_bot_webhook`: принимать только от заранее сконфигурированного источника с HMAC/signature, timestamp/replay protection и idempotency key; JSON из чат-сообщения не доверять.
- `admin_attested`: это подтверждение админа, но **не** событие Telegram; так и показывать в интерфейсе.
- `unverified_text`: никогда не меняет статус наказания.
- Если несколько инцидентов на одного юзера, связь действия с конкретным сообщением может быть неясной. Показывай «действие над пользователем подтверждено, связь с кейсом не установлена», пока человек не свяжет их.
- Админский callback требует ID и права, доступ проверять при обработке, а не при создании кнопки.

## 10. Хранение и отказоустойчивость

- Сначала сохраняй update и derived records, затем подтверждай приём Telegram. Внешние отправки — отдельный transactional outbox.
- Idempotency keys для входящих событий, AI jobs, incidents, reports, feedback, alerts.
- Конкурирующие воркеры должны безопасно брать задачи; lease expiry + retry backoff + dead-letter state с возможностью повторной попытки.
- На HTTP timeout результат отправки Telegram может быть неизвестен; в логах/карточках не объявляй exactly-once гарантию.
- Запускай миграции предсказуемо; поддерживай безопасное повторное применение и документируй rollback. Бэкапы/restore tests для production.
- Cleanup job по retention и лимиту 1000 сообщений **на чат** с сохранением отдельно необходимого audit/evidence и актуальных агрегатов.
- Никогда не пересылай весь backlog 1000 сообщений в AI по умолчанию.
- Размер raw update, SQL rows, JSON ответа LLM и количество запросов за секунду лимитировать.
- Метрики и health endpoint должны быть доступны локально/внутри docker network, не публикуй админские функции в интернет.

## 11. Тестирование: обязательно перед завершением каждой фазы

Минимальная матрица:

- `go test ./...`, `go vet ./...`, `go test -race ./...` по возможности CI.
- Миграции up/down/up на чистой тестовой базе, целостность FK, уникальные индексы, concurrency queue.
- Табличные unit tests четырёх MUST triggers и trust discount — каждый must обходит trust и optional budget.
- URL normalization: URL/entity/caption/text_link, Unicode/IDN, subdomain confusables, Telegram bot link vs обычный t.me username.
- Mock Telegram updates и fake AI API. Тесты не должны зависеть от аккаунта Telegram или настоящих платных запросов.
- Настоящий `/mute` текстовый от обычного пользователя не создаёт `verified`; admin click «спам» не создаёт `ban`.
- Confirmed `chat_member` со статусными переходами и actor, `restricted` права, отсутствие actor в интеграции.
- First observed сохраняется между рестартами; повторный update/edit не удваивает сообщение и stats.
- Сообщение с текстом «ignore all instructions» не изменяет классификатор или конфигурацию.
- Reports reply-only, dedup, массовые жалобы, unknown target.
- LLM: malformed JSON, timeout, 429, 5xx, exhausted optional budget, `AI pending`, crash/retry.
- Логи без токенов/паролей и нет выхода приватных сообщений за срок хранения.

Любой баг с ложным подтверждением санкции, пропуском mandatory AI job, утечкой токена или небезопасной авторизацией — **release blocker**.

## 12. Практика работы кодового агента

**Перед началом фазы:**

1. Коротко укажи, какие пункты `Task.md` реализуются и чем будут проверяться.
2. Проверь текущее состояние git/worktree и тестов, не затирай пользовательские изменения.
3. При внешнем API или сторонней библиотеке посмотри актуальную официальную документацию; не используй несуществующие типы/методы по памяти.
4. Начни с небольшого вертикального среза (input → DB → score → observable output), а не с огромной невыполненной архитектуры.

**Во время реализации:**

- Изменения делать атомарно по смыслу, держать master/build зелёным.
- Для каждого нового модуля сразу добавлять tests и error paths.
- Когда задача требует выбора, предпочитай минимальное работающее решение с расширяемым интерфейсом; технические tradeoffs записывай в `docs/decisions/`.
- Не генерируй бессмысленные комментарии, 100-строчные README без практических команд или code stubs со статусом «готово».
- Не меняй правила продукта и весовые таблицы silently; у всех изменений должны быть tests и запись версии.
- Не подключай MTProto без завершённого Bot API MVP и явного feature flag.

**После завершения фазы:**

1. Запусти форматирование, статический анализ, unit/integration tests и документируй реальные результаты.
2. Сверь реализованное с acceptance criteria соответствующей фазы.
3. Обнови README, образец конфигурации, migration notes и список ограничений.
4. Сообщи: что работает, что протестировано, что ещё не реализовано, какие ручные проверки необходимы.
5. Если не хватает реального API-ключа/админского доступа, обеспечь рабочий mock/dry-run путь и честно обозначь блокер вместо заявления, что всё проверено в production.

## 13. README и релиз — требования к удобству

README должен позволять новому пользователю с Ubuntu VPS запустить сервис самостоятельно:

1. Что делает бот, ограничения Bot API, что **не банит**.
2. Требования (Go для dev, Docker + Compose для production, Postgres), создание бота, выбор privacy mode, настройка admin/chat IDs.
3. Полный quick start с `git clone`, копированием `.env.example`, запуском Compose и миграциями.
4. Как проверить, что бот действительно получает сообщения и `chat_member` updates.
5. Как подключить LLM endpoint и модель; настраиваемая стоимость, mandatory rules, graceful degradation.
6. Команды report и admin feedback, примеры карточек без секретов.
7. Как настраивать пороги, whitelist, retention, health/status, как восстановить бэкап и обновить контейнер.
8. Troubleshooting: BotFather privacy mode, отсутствие `chat_member`, бот не может писать в ЛС, API 429, нерабочие deep links, недоступен AI.

Подготовить корректный `Dockerfile` со сборкой multi-stage, non-root user, healthcheck; `compose.yaml` с сохранением БД, переменными окружения и restart policy. Никаких зависимостей на локальные абсолютные пути разработчика.

## 14. Приоритеты при неоднозначностях

1. Безопасность и отсутствие ложных фактов.
2. Выполнение обязательных проверок и сохранение событий.
3. Воспроизводимость и тесты.
4. Низкая стоимость LLM и низкий шум для модераторов.
